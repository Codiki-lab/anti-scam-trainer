# Avito Start — заскриптованные чаты тренажёра

> Контентная спецификация для MVP антискам-тренажёра.
> Роли: покупатель и продавец.
> Уровни: L1 — обучение, L2 — перенос навыка, L3 — гибридный сценарий.
> Все ссылки, номера заказов и имена вымышлены.

---

## 1. Как использовать документ

Этот файл описывает готовые сценарии для интерфейса в стиле Avito Messenger. Он задаёт:

- контекст объявления;
- сообщения собеседника;
- варианты ответа пользователя;
- оценку каждого решения по шкале 1–4;
- заскриптованную реакцию собеседника;
- финальное последствие;
- разбор после завершения диалога;
- связь ошибки с темой теории.

Во время диалога интерфейс **не сообщает**, правильный ли ответ выбрал пользователь. Реплика собеседника появляется как естественное продолжение разговора. Баллы, красные флаги и безопасный вариант показываются только на экране результата.

### Шкала решений

| Балл | Значение |
|---:|---|
| 4 | Риск распознан, опасное действие отклонено, предложен безопасный способ продолжить сделку |
| 3 | Пользователь не совершает опасное действие, но не называет безопасную альтернативу |
| 2 | Пользователь сомневается, но всё ещё допускает контакт с опасной ссылкой, каналом или схемой |
| 1 | Пользователь выполняет требование мошенника или передаёт чувствительные данные |

### Общие правила реализации

1. Ссылки в сценариях должны быть визуальными макетами и не должны открываться.
2. Слово «Avito» в тексте собеседника не является признаком безопасности.
3. Системные события Avito визуально отличаются от обычных сообщений пользователя.
4. После любого варианта сценарий продолжается. Ошибка не обрывает тренировку мгновенно.
5. В L1 и L2 оценка полностью детерминирована полем `score`.
6. В L3 заскриптованные ответы оцениваются детерминированно, свободный текст — evaluator-моделью.
7. Для MVP итоговый балл можно считать отдельно от контента; сценарии не фиксируют формулу агрегации.

## 1.1. Ограничения Qwen3-8B

В документе под «Qwen» понимается `qwen3:8b` / `Qwen3-8B`, а не модель на 3,8 млрд параметров. Если будет выбрана другая версия, бюджет нужно пересчитать её родным tokenizer-ом.

У Qwen3-8B нативное окно составляет 32 768 токенов; расширение окна не следует считать способом повышения надёжности. Ollama может показывать для своего образа другое максимальное значение, а фактически выделенное окно зависит от конфигурации запуска. Поэтому backend должен задавать `num_ctx` явно и не полагаться на значение по умолчанию.

### Почему нельзя передавать модели все документы

На момент подготовки файла объём двух основных документов составляет:

| Документ | Символов без учёта байтов UTF-8 |
|---|---:|
| Master-context | около 20 840 |
| Этот файл сценариев | около 49 900 |
| Итого до глоссария | около 70 740 |

Точное число токенов зависит от версии tokenizer-а. Для защитного расчёта используется грубая верхняя оценка **1 токен на 2 символа** для смешанного русского текста, таблиц и ID. Тогда два файла могут занять около **35 370 токенов**. Уже без отдельного глоссария, chat template, истории и места под ответ это превышает нативное окно.

Следовательно:

> Полные master-context, глоссарий и каталог сценариев никогда не передаются Qwen во время диалога.

Backend заранее выбирает один сценарий и собирает компактный runtime-пакет только из релевантных фрагментов.

## 1.2. Рабочий бюджет контекста

### Основной профиль MVP

```text
model: qwen3:8b
num_ctx: 8192
thinking: false
max generated tokens, scammer: 120
max generated tokens, evaluator: 240
```

`8192` — не максимальная возможность модели, а контролируемое рабочее окно. Оно оставляет большой запас и не провоцирует команду складывать в prompt всю базу знаний.

### Целевой бюджет одного запроса

| Часть runtime prompt | Лимит, токенов | Содержание |
|---|---:|---|
| System contract | 350 | Роль модели, запреты, формат и правило «не выдумывать факты» |
| Platform facts | 250 | Только 8–12 правил Avito, нужных текущей роли |
| Active glossary | 180 | Только термины текущего риска и встреченные в реплике синонимы |
| Role safety knowledge | 450 | Правила покупателя **или** продавца, не обе роли |
| Scenario seed | 300 | Товар, цена, цель мошенника, разрешённые тактики и факты |
| State + compact summary | 300 | Текущая фаза, уже показанные сигналы, решения пользователя |
| Rolling history | 900 | Не более трёх последних пар реплик |
| Current user message | 220 | Ответ пользователя после ограничения длины |
| Task + output schema | 350 | Одна задача и компактная JSON schema |
| **Целевой input** | **3 300** | Верхняя граница перед генерацией |
| Generated output | 120 / 240 | Отдельный лимит для scammer / evaluator |

При `num_ctx=8192` остаётся минимум 4 652 токена технического запаса. Рабочий профиль должен быть явно выставлен в 8 192.

Профиль `4096` не удовлетворяет правилу 75% при input в 3 300 токенов. Если инфраструктура не позволяет выделить `8192`, backend обязан переключиться на отдельный compact-профиль: input не более 2 400 и output не более 200 токенов. Это аварийный режим для L3 evaluator-а, а не рекомендуемая конфигурация генеративного L4.

### Жёсткая проверка перед каждым вызовом

```text
estimatedInputTokens + maxOutputTokens <= 0.75 × num_ctx
```

Для `num_ctx=8192` мягкий порог равен `6144`, но проект целится в `3300`. Если prompt превысил целевой бюджет, backend сокращает его в таком порядке:

1. удаляет старые реплики, сохраняя последние три пары;
2. заменяет удалённую историю структурированным summary;
3. оставляет только glossary-модуль активного `riskType`;
4. убирает примеры, уже не связанные с текущей фазой;
5. при превышении 75% не вызывает модель и использует scripted fallback.

Токены считаются tokenizer-ом той же версии Qwen, которая запущена в production. Оценка по символам допустима только как временный защитный fallback. После ответа backend также сохраняет фактические `prompt_eval_count` и `eval_count` из Ollama для наблюдения за реальным расходом.

## 1.3. Что попадает в runtime-контекст

Вместо одного большого файла база знаний разбивается на модули:

```text
platform_core
role_buyer_core | role_seller_core
risk_phishing | risk_prepayment | risk_fake_payment | ...
glossary_common
glossary_<active_risk>
scenario_<scenario_id>
```

На один запрос разрешён следующий набор:

```text
platform_core
+ один role-модуль
+ один основной risk-модуль
+ при необходимости один дополнительный risk-модуль
+ glossary_common в сокращённом виде
+ glossary активного риска
+ только текущий scenario seed
```

Нельзя одновременно передавать:

- знания покупателя и продавца;
- все типы мошенничества;
- все примеры сленга;
- соседние сценарии;
- пользовательскую теорию целиком;
- результат предыдущей тренировки;
- внутреннее thinking-содержимое модели.

## 1.4. Разделение вызовов модели

Один prompt не должен одновременно играть мошенника, оценивать пользователя и решать, завершён ли урок.

| Компонент | Кто управляет | Использование Qwen |
|---|---|---|
| L1 и L2 | State machine backend-а | Не используется |
| Реплики и переходы L1/L2 | Контент из этого файла | Не используются генерации |
| Оценка choices L1/L2 | Backend по `answerId` | Не используется |
| Реплики L3 | Scripted flow | Не используется |
| Оценка free text L3 | Отдельный evaluator | Один stateless-вызов на ответ |
| Реплики L4 | Scammer generator в рамках seed | Один короткий вызов на ход |
| Оценка free text L4 | Отдельный evaluator | Отдельный stateless-вызов |
| Фаза и завершение сценария | Backend | Модель не принимает финальное решение |

Это означает, что **8 из 10 текущих сценариев вообще не зависят от качества Qwen**, а два L3 используют модель только как классификатор смысла.

## 1.5. Ограничение длины чатов

### L1 и L2

- не более 3 решений пользователя;
- не более 8 сообщений вместе с системным финалом;
- история не отправляется в модель.

### L3

- 1 scripted choice;
- не более 2 свободных ответов;
- evaluator получает текущий ответ, компактный контекст шага и не более двух предыдущих сообщений;
- после второй free-text точки сценарий завершается backend-ом независимо от вывода модели.

### L4

- не более 6 ответов пользователя;
- не более 6 сгенерированных реплик мошенника;
- не более 3 последних пар реплик в rolling history;
- после 4-й пары создаётся compact summary до 250 токенов;
- фазы фиксированы: `hook → escalation → critical_request → resolution`;
- одна фаза занимает не более двух ответов пользователя;
- модель не может вернуться в предыдущую фазу или придумать новый тип мошенничества.

Лимит в шесть ходов выбран не как «момент поломки» Qwen: у модели нет точной границы, после которой внезапно начинаются галлюцинации. Это продуктовый предел, при котором четырёхфазный сюжет успевает раскрыть риск, а накопление ошибок и дрейф роли остаются ограниченными. Благодаря rolling history размер prompt почти не растёт от первого до шестого хода.

Backend завершает L4 при первом выполненном условии:

```text
user_safe_exit
critical_unsafe_action
turn_count >= 6
phase == resolution
two_invalid_model_outputs
token_budget_exceeded
```

При лимите ходов показывается нейтральное системное завершение:

> Диалог завершён. Перейдём к разбору ваших решений.

Модель не генерирует финальное последствие самостоятельно.

## 1.6. Антигаллюцинационные ограничения

### Scammer generator может

- использовать только факты из `scenario seed`;
- выбрать одну тактику из `allowedTactics` текущей фазы;
- написать одну реплику до 280 символов;
- сослаться только на уже введённые в сценарий товар, цену и способ сделки;
- вернуть структурированный ответ.

### Scammer generator не может

- менять товар, цену, имя, роль и тип риска;
- придумывать новые правила Avito;
- утверждать реальные юридические или банковские факты;
- создавать рабочие URL, телефоны, карты и реквизиты;
- давать пользователю инструкции вне учебного сценария;
- добавлять нового персонажа без разрешения seed-а;
- продолжать диалог после команды `END_SCENARIO`.

### Минимальный ответ scammer-а

```json
{
  "message": "Одна короткая реплика собеседника",
  "tactic": "urgency",
  "phase": "escalation"
}
```

Backend валидирует:

- JSON schema;
- длину `message`;
- `tactic` по allowlist;
- соответствие `phase` текущему состоянию;
- отсутствие URL, телефона, номера карты и нового денежного значения;
- отсутствие терминов из другого сценария.

Если проверка не пройдена, ответ не показывается пользователю. Допускается одна повторная генерация с коротким repair-prompt. После второй ошибки используется заранее написанная fallback-реплика и сценарий переходит к завершению.

Невозможно гарантировать, что генеративная модель внутренне никогда не галлюцинирует. Гарантия продукта формулируется иначе:

> Ни один невалидный, вышедший за сценарий или не прошедший policy-проверку ответ модели не показывается пользователю.

### Evaluator

Evaluator работает в `thinking: false`, с низкой вариативностью и JSON schema на уровне API. Он не продолжает чат и не пишет новую историю. Его задача ограничена шестью полями:

```json
{
  "score": 1,
  "is_safe": false,
  "risk_type": "phishing",
  "detected_signals": ["переход по внешней ссылке"],
  "evaluation": "Пользователь допускает опасное действие",
  "safe_action": "Проверить заказ внутри приложения"
}
```

Backend дополнительно проверяет диапазон `score`, допустимые enum-значения и длину текста. При невалидном JSON используется повторная попытка без истории. Если она тоже невалидна, применяется fallback-оценка «нужна повторная проверка» без начисления окончательного результата.

## 1.7. Рекомендуемые параметры генерации

Для диалогового generator-а:

```text
thinking: false
temperature: 0.3
top_p: 0.8
top_k: 20
num_predict: 120
repeat_penalty: 1.1
```

Для evaluator-а:

```text
thinking: false
temperature: 0
num_predict: 240
format: JSON schema
```

`num_predict` используется в нативном Ollama API; при OpenAI-compatible endpoint ему соответствует `max_tokens`.

Низкая температура сама по себе не устраняет галлюцинации. Главные меры — маленький релевантный контекст, state machine, allowlist, schema validation, ограничение ходов и scripted fallback.

## 1.8. Метрики, которые нужно сохранять

Для каждого AI-вызова:

```text
model
scenarioId
phase
turnIndex
numCtx
promptEvalCount
evalCount
finishReason
schemaValid
policyValid
usedRetry
usedFallback
latencyMs
```

Сигналы для остановки релиза:

- p95 `promptEvalCount` выше 4 500;
- хотя бы 1% ответов не проходит schema после retry;
- модель меняет товар, цену или тип мошенничества;
- generator выдаёт больше одной реплики;
- L4 выходит за 6 пользовательских ходов;
- fallback вызывается чаще согласованного командой порога.

До запуска L4 необходимо прогнать фиксированный набор безопасных, опасных, двусмысленных и сленговых ответов на каждом `riskType`.

### Обозначения

- **Собеседник** — потенциальный мошенник.
- **Пользователь** — человек, проходящий тренировку.
- **Система** — нейтральное системное сообщение тренажёра или Avito.
- **Реакция** — следующая реплика, зависящая от выбранного ответа.
- **Сведение** — общая реплика, к которой возвращаются все ветки.

# 2. Покупатель

## Buyer L1 — Поддельная Avito Доставка

### Карточка сценария

| Поле | Значение |
|---|---|
| `id` | `buyer-l1-fake-delivery` |
| Роль пользователя | Покупатель |
| Уровень | 1 |

| Тема теории | `buyer-phishing-links` |

| Цель мошенника | Увести покупателя на поддельную страницу оплаты |
| Учебная цель | Проверять заказ внутри приложения и не доверять ссылкам из чата |

### Вступление

**Максим:**

> Добрый день! Да, телефон ещё продаётся. Состояние отличное, аккумулятор 91%.

### Шаг 1 — выбор способа сделки

**Ответы пользователя:**

| ID | Текст | Балл | Что проверяем |
|---|---|---:|---|
| `buyer-l1-s1-a` | Можно оформить покупку через Avito Доставку внутри приложения? | 4 | Безопасный канал сделки |
| `buyer-l1-s1-b` | Скиньте больше фото в Telegram, там и договоримся | 2 | Готовность уйти из защищённого чата |
| `buyer-l1-s1-c` | Могу сразу перевести деньги вам на карту | 1 | Прямой перевод незнакомому продавцу |

**Реакции:**

- После `a`: «Можно, но обычное оформление у меня сейчас почему-то не работает.»
- После `b`: «Да, давайте. Но чтобы не терять время, я уже сделал форму доставки.»
- После `c`: «Так даже быстрее. Только сначала подтвердите покупку через мою форму.»

**Сведение — Максим:**

> Я сам создал заявку на Avito Доставку. Вот ссылка, там уже всё заполнено:
> `avito-order.example/74291`
> Оплатите, и я сегодня же отправлю.

### Шаг 2 — внешняя ссылка

**Ответы пользователя:**

| ID | Текст | Балл | Что проверяем |
|---|---|---:|---|
| `buyer-l1-s2-a` | По ссылке не пойду. Сам открою приложение и проверю, появился ли заказ | 4 | Отказ плюс безопасная альтернатива |
| `buyer-l1-s2-b` | Открою, просто посмотрю, но карту вводить не буду | 2 | Риск уже при переходе на фишинговый сайт |
| `buyer-l1-s2-c` | Хорошо, сейчас оплачу по ссылке | 1 | Оплата на стороннем сайте |

**Реакции:**

- После `a`: «В приложении заказ не появится, пока вы не подтвердите его по ссылке.»
- После `b`: «Там безопасно, страница один в один как Avito. Просто следуйте инструкции.»
- После `c`: «Отлично. Введите данные карты, потом придёт код подтверждения.»

**Сведение — Максим:**

> Только быстрее, пожалуйста. На телефон ещё двое претендуют, через пять минут отдам другому.

### Шаг 3 — давление срочностью

**Ответы пользователя:**

| ID | Текст | Балл | Что проверяем |
|---|---|---:|---|
| `buyer-l1-s3-a` | Тогда откажусь от сделки и пожалуюсь на ссылку. Покупки оформляю только внутри Avito | 4 | Прекращение опасной сделки и жалоба |
| `buyer-l1-s3-b` | Подождите пять минут, я сначала проверю всё в приложении | 3 | Пауза и проверка без явного отказа от ссылки |
| `buyer-l1-s3-c` | Ладно, ввожу данные карты, только никому не продавайте | 1 | Решение под влиянием срочности |

### Финал диалога

**Система:**

> Тренировка завершена. Разберём, какие признаки указывали на мошенничество.

### Разбор на экране результата

**Красные флаги:**

- продавец утверждает, что штатная Avito Доставка «не работает»;
- присылает внешнюю ссылку якобы на уже созданный заказ;
- просит ввести платёжные данные вне приложения;

## 4.1. Сколько здесь развилок

Термин «развилка» нужно считать на трёх уровнях:

| Метрика | Количество | Что означает |
|---|---:|---|
| Контрольные точки | 20 | Места, где пользователь выбирает один готовый ответ |
| Готовые варианты ответа | 60 | В каждой контрольной точке по 3 варианта |
| Free-text точки | 4 | Открытые ответы в двух сценариях L3 |
| Полные scripted-маршруты L1/L2 | 108 | Все математически возможные комбинации выборов внутри полностью заскриптованных чатов |
| Scripted-префиксы L3 | 6 | По 3 варианта первого выбора в двух L3 перед свободным текстом |
| Детерминированные маршруты и префиксы всего | 114 | 108 конечных L1/L2-маршрутов плюс 6 входов в свободную часть L3 |

Расчёт полных scripted-маршрутов:

```text
Buyer L1:     3 × 3 × 3 = 27
Buyer L2-A:   3 × 3     = 9
Buyer L2-B:   3 × 3     = 9
Buyer L2-C:   3 × 3     = 9
Seller L1:    3 × 3 × 3 = 27
Seller L2-A:  3 × 3     = 9
Seller L2-B:  3 × 3     = 9
Seller L2-C:  3 × 3     = 9
                             ───
Итого L1/L2:                  108
```

L3 имеет по одной scripted-точке с тремя вариантами, а затем свободный ввод. Поэтому количество полных L3-маршрутов математически не ограничено, но количество написанных вручную входов в свободную часть равно `2 × 3 = 6`.

Ветки после каждого готового ответа сходятся обратно в общий сценарий. Поэтому `108` маршрутов не означают, что нужно хранить 108 отдельных текстов: backend хранит 18 контрольных точек L1/L2, 54 ответа и локальные реакции на них.

## 4.2. Посимвольная длина текущих чатов

Метод расчёта одной пройденной ветки:

```text
длина ветки =
  все обязательные сообщения
  + один выбранный ответ в каждой scripted-точке
  + одна соответствующая реакция на каждый нефинальный выбор
  + фактические free-text ответы пользователя
```

Считаются Unicode-символы видимого текста. Не считаются Markdown-разметка, заголовки, таблицы, ID, пояснения для команды, экран результата, имена JSON-полей и служебные инструкции prompt-а.

Для L3 используются два режима:

- типичный свободный ответ — 120 символов;
- жёсткий лимит одного свободного ответа — 400 символов.

| Сценарий | Контрольные точки | Варианты | Free text | Сообщений в ветке | Фиксированный текст, символов | Scripted min–max, символов | Типичная ветка | Максимальная ветка | Защитная оценка токенов, типичная / max |
|---|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| Buyer L1 — доставка | 3 | 9 | 0 | 9 | 377 | 629–736 | 736 | 736 | 368 / 368 |
| Buyer L2-A — предоплата | 2 | 6 | 0 | 8 | 342 | 452–559 | 559 | 559 | 280 / 280 |
| Buyer L2-B — мессенджер | 2 | 6 | 0 | 6 | 275 | 396–488 | 488 | 488 | 244 / 244 |
| Buyer L2-C — SMS-код | 2 | 6 | 0 | 7 | 318 | 400–546 | 546 | 546 | 273 / 273 |
| Buyer L3 — камера | 1 | 3 | 2 | 9 | 538 | 625–683 | 923 | 1 483 | 462 / 742 |
| Seller L1 — получение оплаты | 3 | 9 | 0 | 9 | 366 | 610–741 | 741 | 741 | 371 / 371 |
| Seller L2-A — скриншот | 2 | 6 | 0 | 6 | 259 | 363–497 | 497 | 497 | 249 / 249 |
| Seller L2-B — страховка | 2 | 6 | 0 | 7 | 425 | 532–627 | 627 | 627 | 314 / 314 |
| Seller L2-C — лжеподдержка | 2 | 6 | 0 | 7 | 437 | 548–660 | 660 | 660 | 330 / 330 |
| Seller L3 — скрытый заказ | 1 | 3 | 2 | 9 | 488 | 559–616 | 856 | 1 416 | 428 / 708 |

Последний столбец использует ту же защитную оценку `1 токен ≈ 2 символа`. Это не точный результат tokenizer-а Qwen, а верхнеуровневый запас для проектирования.

### Вывод по текущим чатам

- самый длинный полностью scripted-чат — Seller L1: до 741 символа видимой переписки;
- самый длинный L3 при типичных ответах — Buyer L3: около 923 символов;
- самый длинный L3 при двух ответах по 400 символов — Buyer L3: около 1 483 символов;
- даже максимальная видимая переписка L3 консервативно занимает меньше 750 токенов;
- основной расход контекста создаёт не сама переписка, а system contract, знания роли, правила платформы, глоссарий и JSON schema.

Сообщения L1/L2 в Qwen не передаются, потому что эти уровни полностью выполняются state machine. Токены для них приведены только для сравнения длины контента.

## 4.3. Расчёт вызовов evaluator-а для L3

Evaluator не получает весь чат и весь документ. Для расчёта используются:

```text
evaluator base package:
  system contract             350
  platform facts              250
  active glossary             180
  role knowledge              450
  output task + JSON schema   350
                              ────
  invariant subtotal        1 580 токенов
```

Оставшаяся часть зависит от точки сценария:

| Вызов | Base | Scenario + step state | Недавняя история | Текущий ответ | Итого типично | Итого при ответе 400 символов |
|---|---:|---:|---:|---:|---:|---:|
| L3, первая free-text точка | 1 580 | 450 | 300 | 60 / 200 | 2 390 | 2 530 |
| L3, вторая free-text точка | 1 580 | 450 | 500 | 60 / 200 | 2 590 | 2 730 |

Здесь 120 символов пользовательского ответа считаются примерно как 60 токенов, а максимальные 400 символов — как 200 токенов. Верхняя оценка второго вызова `2730` остаётся на 570 токенов ниже целевого input-лимита `3300`.

В историю evaluator-а не добавляется его предыдущий JSON-ответ. Для второй точки backend передаёт только структурированное резюме предыдущего решения, например:

```json
{
  "previous_score": 3,
  "previous_intent": "refused_prepayment",
  "risk_acknowledged": true
}
```

## 4.4. Как растёт контекст L4 по ходам

Для расчёта берётся консервативный generator-пакет:

```text
system + platform + glossary + role + seed + schema = 1 880 токенов
state / summary                                      =   300 токенов
current user message                                 =   220 токенов max
одна сохранённая пара user + scammer                 =   300 токенов target
```

| Ход пользователя | Сохранённых предыдущих пар | Верхняя оценка input | Эквивалент при 2 символах на токен | Действие backend-а |
|---:|---:|---:|---:|---|
| 1 | 0 | 2 400 токенов | около 4 800 символов | Обычный вызов |
| 2 | 1 | 2 700 токенов | около 5 400 символов | Обычный вызов |
| 3 | 2 | 3 000 токенов | около 6 000 символов | Обычный вызов |
| 4 | 3 | 3 300 токенов | около 6 600 символов | Достигнут целевой input-лимит |
| 5 | 3 + summary | не более 3 300 | не более 6 600 символов | Старейшая пара заменяется summary |
| 6 | 3 + summary | не более 3 300 | не более 6 600 символов | Последний разрешённый ход |

Контекст перестаёт расти после четвёртого хода. Если три полные пары вместе превышают 900 токенов, backend хранит только две пары и summary. После шестого ответа пользователя сценарий завершается независимо от оставшегося места в окне.

При `num_ctx=8192` и generator output до 120 токенов максимальный рабочий вызов занимает:

```text
3 300 input
+ 120 output
= 3 420 токенов

3 420 / 8 192 ≈ 41,7% окна
```

Таким образом, в рабочем профиле всегда остаётся около 58% окна. Лимит в шесть ходов защищает прежде всего от сюжетного дрейфа маленькой модели, а не от физического переполнения контекста.

## 4.5. Ограничения сообщений для будущих prompt-ов

| Объект | Лимит |
|---|---:|
| Готовый answer option | 140 символов |
| Реплика scripted-собеседника | 280 символов |
| Реплика L4 scammer generator | 280 символов и не более 120 токенов |
| Free-text пользователя | 400 символов и не более 220 токенов после tokenization |
| Compact summary | 500 символов и не более 250 токенов |
| `evaluation` evaluator-а | 240 символов |
| `safe_action` evaluator-а | 200 символов |
| Один detected signal | 60 символов, максимум 3 элемента |

Если одновременно сработал символьный и токенный лимит, применяется меньший из них. Перед следующим этапом — генерацией prompt-ов — эти лимиты должны стать частью JSON schema и backend validation, а не только текстовой инструкцией модели.

| Средний | «Основной риск замечен, но мошенник получил шанс продолжить» |
| Низкий | «Собеседнику удалось подтолкнуть вас к опасному действию» |

Не использовать обвиняющие формулировки вроде «Вы повелись» или «Это было глупо». Задача результата — объяснить момент принятия решения и закрепить безопасное действие.

---

# 6. Контентные требования перед переносом в код

- Не превращать ответы в очевидную пару «правильный / абсурдный»; опасные варианты должны звучать правдоподобно.
- Не показывать полные реквизиты реальных карт, телефонов и аккаунтов.
- Не использовать настоящие фишинговые домены; только зарезервированный `.example`.
- Не изображать обычную Avito Доставку как опасную. Опасна ссылка или инструкция собеседника вне штатного интерфейса.
- Не утверждать, что любой прямой перевод всегда является мошенничеством; в сценариях риск создаёт совокупность признаков и отсутствие подтверждения.
- Реплики должны помещаться в мобильные чат-бабблы без длинных лекций.
- Теоретическое объяснение показывается после диалога, а не устами мошенника.
- Для L2 при повторном запуске выбирать другой `scenarioId`, если это возможно.

---

# 7. Что остаётся для Level 4

Level 4 не хранится как полный скрипт, но остаётся конечным автоматом с четырьмя фазами и максимум шестью ответами пользователя. Для него из сценариев выше можно подготовить контролируемые `scenario seed`:

```text
role
scamType
product
price
scammerGoal
initialSituation
allowedTactics
forbiddenTactics
successCondition
stopCondition
difficulty
maxUserTurns
fallbackMessagesByPhase
```

AI-собеседник не должен менять тип мошенничества посреди диалога, запрашивать реальные данные или генерировать активные ссылки. После каждого свободного ответа отдельный evaluator оценивает действие пользователя по шкале 1–4. Backend, а не AI, переключает фазы, считает ходы и завершает сценарий по правилам из раздела 1.5.
