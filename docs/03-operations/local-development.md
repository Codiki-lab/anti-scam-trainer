# Локальная разработка

## Что потребуется

- Go версии, совместимой с `go 1.26.5` из `backend/go.mod`;
- Docker с поддержкой Compose;
- `make`;
- свободные локальные порты `3000`, `5432`, `8080` и, при работе с моделью, `11434`.

Docker-сборка включает Node.js и собирает веб-клиент внутри образа gateway, поэтому для запуска Compose Node.js на машине не нужен. Node.js нужен только для локальной разработки и запуска проверок фронтенда.

## Подготовка

Из корня репозитория:

```bash
make setup
```

Команда подготавливает `backend/.env`, создаёт `frontend/.env` из примера (если он есть) и загружает Go-модули. Если `frontend/package.json` отсутствует, установка фронтенда пропускается.

`make env` можно запускать отдельно: он создаёт `backend/.env`, если файла нет, и добавляет в существующий файл переменные, отсутствующие в `backend/.env.example`. Уже заданные значения не меняются. Все Docker Compose-команды читают этот файл напрямую, поэтому конфигурация одинаково передаётся сборке, миграциям и API.

Все цели Makefile используют единый Compose-проект `anti-scam-trainer`, поэтому Docker Desktop показывает сервисы в одной группе. Сервисы Ollama находятся в профиле `ollama`: обычные команды их не запускают, а цели с суффиксом `-ollama` включают профиль.

`make up` передаёт контейнеру API параметры соединения сам. Пример окружения уже содержит параметры, нужные для запуска API на машине через `go run ./cmd/api`:

```dotenv
POSTGRES_HOST=localhost
POSTGRES_PORT=5432
POSTGRES_NAME=antiscam
PORT=8080
LOG_LEVEL=debug
LOG_FOLDER=out/logs
```

`POSTGRES_NAME` должен совпадать с `POSTGRES_DB`.

## Конфигурация аутентификации

Для запуска API необходимы переменные, которые не следует коммитить:

```dotenv
JWT_SECRET=<случайный секрет подписи JWT>
ADMIN_USERNAME=<логин единственного администратора>
ADMIN_PASSWORD=<пароль единственного администратора>
SWAGGER_USERNAME=<логин для документации API>
SWAGGER_PASSWORD=<пароль для документации API>
```

При отсутствии любой из `JWT_SECRET`, `ADMIN_USERNAME`, `ADMIN_PASSWORD`, `SWAGGER_USERNAME` или `SWAGGER_PASSWORD` API завершает запуск с ошибкой. При старте приложение создаёт единственную учётную запись с ролью `admin`, если её ещё нет. Обычная регистрация создаёт только пользователей с ролью `user`.

`SWAGGER_USERNAME` и `SWAGGER_PASSWORD` защищают только документацию: они не создают учётную запись Пользователя и не заменяют JWT-cookie. После запуска Swagger UI доступен по `http://localhost:8080/swagger/`, а OpenAPI v1 — по `http://localhost:8080/openapi/v1.yaml`; оба URL запрашивают HTTP Basic Auth. Адрес без завершающего слеша (`/swagger`) перенаправляет на `/swagger/`. Полный контракт хранится в `backend/openapi/v1/openapi.yaml`.

## Rate limits и trusted proxy

Без настройки backend допускает 5 регистраций за 10 минут на client IP, 10 входов за 10 минут на сочетание IP и нормализованного Логина, 10 AI-ответов за минуту и 5 стартов Свободной игры за минуту на Пользователя. Значения задаются `RATE_LIMIT_*_CAPACITY` и `RATE_LIMIT_*_WINDOW`; `RATE_LIMIT_MAX_BUCKETS` и `RATE_LIMIT_BUCKET_TTL` ограничивают память. Нулевые и некорректные значения останавливают запуск.

По умолчанию forwarding headers не доверяются. `TRUSTED_PROXY_CIDRS` перечисляет непосредственные proxy-сети через запятую. Compose передаёт `172.16.0.0/12`, поэтому Nginx gateway может передать `X-Forwarded-For`; прямой публичный клиент не может подменить ключ limiter. Для запуска backend напрямую оставьте переменную пустой.

## PostgreSQL

Запуск контейнера:

```bash
make build
make up
```

`make build` собирает образы, включая production-сборку веб-клиента внутри образа Nginx gateway. `make up` запускает только уже собранные образы и не выполняет неявную пересборку. Перед стартом одноразовый контейнер `anti-scam-trainer-migrate` применяет все ещё не применённые миграции из `backend/migrations`; API ждёт его успешного завершения. После изменения кода или Dockerfile снова выполните `make build`, затем `make up`.

PostgreSQL доступен на `localhost:5432` через контейнер `port-forwarder`, а API — на `http://localhost:8080`. Данные сохраняются в `out/pgdata`.

Миграции имеют парные файлы `<версия>_<имя>.up.sql` и `<версия>_<имя>.down.sql`. Для ручного управления доступны:

```bash
make migrate-up
make migrate-down
```

`migrate-down` откатывает одну последнюю миграцию и может удалить данные, созданные этой миграцией. В частности, откат `000002_training_model` удаляет ответы шагов и прохождения свободной игры, которых не было в базовой схеме. Выполняйте его только при остановленном API; после отката последующий `make up` вновь применит актуальные миграции.

## Бэкенд

Для отладки API можно запустить его на машине, но сначала поднимите PostgreSQL и примените миграции:

```bash
make up
cd backend
PORT=8081 go run ./cmd/api
```

В этом случае контейнерный API остаётся на порту `8080`, а локальный — на `8081`.

Проверка:

```bash
curl http://localhost:8080/api/v1/health
```

Ожидаемый ответ:

```json
{"status":"ok"}
```

## Ollama

Для полной сборки и запуска PostgreSQL, API, gateway и Ollama одной командой используйте:

```bash
make start-ollama
```

Команда собирает образы, запускает сервисы и загружает модель из `OLLAMA_MODEL`. По умолчанию в примере окружения указана `qwen3:8b`. Первый запуск может занять продолжительное время из-за скачивания модели.

Для раздельного управления по-прежнему доступны `make build-ollama`, `make up-ollama` и `make ollama-init`.

```bash
make logs-ollama
```

Технический AI provider создаётся при старте бэкенда и вызывается Уровнями 3–4 и Свободной игрой. Настройки адреса, модели, таймаута и бюджета окна задаются переменными `OLLAMA_*` из `backend/.env`; их полный список и правила риска описаны в [архитектуре AI provider](../02-architecture/ai-provider.md).

## Остановка

```bash
make down
```

Для конфигурации с Ollama:

```bash
make down-ollama
```

`make clean` удаляет контейнеры и именованные Docker volumes, но каталог `out/pgdata` подключён как bind mount и остаётся на диске.

### Полный сброс локальной БД

```bash
make db-reset
```

Команда останавливает конфигурацию с Ollama и необратимо удаляет `out/pgdata`: локальные Пользователи, Прохождения, Result и прочие не-seed данные будут потеряны. Последующий `make up` или `make start-ollama` применит миграции на чистой БД и восстановит только штатный seed-контент. Backend затем создаст администратора из `ADMIN_USERNAME` и `ADMIN_PASSWORD`.

## Веб-клиент и публичное демо

`make build` собирает веб-клиент с `VITE_API_BASE_URL=/api` внутри образа Nginx gateway. Compose запускает gateway на `http://localhost:3000`: статические файлы и API доступны под одним origin, а `/api/*` проксируется в backend. Для локальной разработки фронтенда используйте `cd frontend && npm run dev`; credentialed CORS в этом режиме разрешён только origin из `FRONTEND_ORIGINS`.

```bash
ngrok http 3000
```

Туннелировать нужно gateway, а не backend: тогда `HttpOnly` cookie и `/api` остаются same-origin. Полная репетиция описана в [чек-листе демонстрации](demo-checklist.md), калибровка модели — в [инструкции qwen3:8b](ai-calibration.md).

### Детерминированный демо-пользователь

После применения миграций можно одной командой пересоздать демонстрационное состояние:

```bash
make demo-reset
```

Команда удаляет только прежнюю учётную запись `demo-seller` и создаёт её заново с паролем `demo1234`. Это возвращающийся продавец: Теория и Quiz первой Темы пройдены, сохранён Result Уровня 1 на 75 Баллов и одно Достижение, а Прохождение Уровня 2 для смартфона оставлено незавершённым. Команду можно безопасно повторять перед каждой демонстрацией; остальные учётные записи и контент она не меняет.

## Проверки

Рабочая на текущем состоянии команда:

```bash
cd backend
go test ./...
```

Статический анализ Go-кода запускается из корня репозитория:

```bash
make lint
```

Для этого нужен `golangci-lint` v2. Его конфигурация находится в [`backend/.golangci.yaml`](../../backend/.golangci.yaml), то есть рядом с `go.mod` и только в области Go-бэкенда. Конфигурация включает стандартный набор линтеров, дополнительно проверяет неявно отброшенные ошибки, проверяет типичные ошибки и опечатки, а также требует форматирование `gofmt`. Best-effort вызовы явно присваивают ошибку `_`; ошибки инфраструктурных вызовов, не отмеченные таким образом, остаются видимыми.

`make test` запускает Go-набор и, если существует `frontend/package.json`, тесты веб-клиента.

После `make build && make up` credentialed путь через Nginx gateway проверяется отдельным прогоном. Он создаёт временного Пользователя, сохраняет cookie Login и запрашивает Dashboard выбранной Ролевой ветки:

```bash
make gateway-regression
```

По умолчанию используется `http://localhost:3000`; для CI или другого адреса gateway задайте `GATEWAY_URL`, например `GATEWAY_URL=http://127.0.0.1:3000 make gateway-regression`.

Контентный acceptance-тест запускается против одноразовой БД после применения миграций:

```bash
cd backend
set -a; source .env; set +a
POSTGRES_TEST_NAME=antiscam_acceptance POSTGRES_HOST=localhost POSTGRES_PORT=5432 go test ./internal/tests/content -count=1
```

Перед публикацией изменения схемы проверяется последовательность `up/down/up` как на чистой БД, так и на предыдущей заполненной схеме с существующими Пользователем, Сценарием, Прогрессом и Result. Ожидаемые seed-количества после `up`: 12 опубликованных Тем, 60 блоков Теории, 60 вопросов Quiz, 240 вариантов Quiz, 48 опубликованных Сценариев, 168 Шагов сценария, 216 вариантов ответа и 144 реакции виртуального собеседника.

Для миграции полного Avito-каталога отдельный harness создаёт одноразовую БД на версии 9, добавляет исторические Result и Прогресс, пользовательский опубликованный Сценарий, применяет версию 10, создаёт Прохождение нового Сценария и проверяет `down/up` с сохранением обеих историй:

```bash
./scripts/test-migration-000010.sh
```
