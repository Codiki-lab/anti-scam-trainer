# Anti-scam trainer — frontend/backend handoff

> Статус: реализованный backend-контракт Issue #49
> Дата: 2026-08-09
> Канонические DTO: [`backend/openapi/v1/openapi.yaml`](../backend/openapi/v1/openapi.yaml)

Документ фиксирует пользовательский путь и правила интеграции 11 экранов. При расхождении примера с OpenAPI источником истины является OpenAPI; изменение внешнего поведения одновременно обновляет handler, contract-тест, OpenAPI и этот handoff.

## Пользовательский путь

```text
регистрация или вход
  → Dashboard и Ежедневное задание
  → шесть Тем выбранной ролевой ветки
  → Теория
  → Quiz
  → Уровни 1–4
  → Result
  → Прогресс и Достижения
  → Свободная игра после L4 во всех шести Темах роли
```

Роль доступа (`user|admin`) и ролевая ветка обучения (`buyer|seller`) — разные понятия. Предпочтительная ветка хранится в `training_role`, но не запрещает Пользователю открыть вторую ветку.

## Транспорт и аутентификация

- Base URL продуктовых маршрутов: `/api/v1`.
- Регистрация, вход, выход и health-check открыты; остальные пользовательские методы требуют JWT в `HttpOnly` cookie `access_token`.
- Frontend всегда отправляет credentialed-запросы и не передаёт `user_id`.
- Для production-сборки рекомендуется same-origin `/api` через Nginx. В dev credentialed CORS разрешён только origin из `FRONTEND_ORIGINS`.
- Каждый ответ содержит `X-Request-ID`.
- Ошибки имеют единый вид:

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "topic_id is required",
    "details": {},
    "request_id": "..."
  }
}
```

`error.request_id` совпадает с `X-Request-ID`. Для повторной отправки ответа после смены Шага используется код `STALE_STEP`. Ошибки AI имеют `AI_UNAVAILABLE`/`AI_INVALID_RESPONSE` и не изменяют Прохождение.

## Экранный контракт

| Экран | Основные методы | Источник состояния |
| --- | --- | --- |
| Регистрация | `POST /auth/register` | `username`, `password`, обязательный `training_role` |
| Вход | `POST /auth/login` | Успех устанавливает auth-cookie |
| Главная | `GET /dashboard?role=...`, `POST /daily-tasks/answer` | Профиль, Серия дней, Темы, превью Достижений, `continue_action` и сохранённое Ежедневное задание |
| Темы | `GET /topics?role=...`, `GET /topics/{id}` | Шесть Тем роли, чтение, Quiz и четыре состояния Уровней |
| Теория | `GET /topics/{id}/theory`, `POST /topics/{id}/theory/read` | Пять структурированных блоков; отметка чтения идемпотентна |
| Quiz | `GET /topics/{id}/quiz`, `POST /topics/{id}/quiz/attempts` | Пять вопросов, четыре варианта, порог 80%; правильность до отправки не раскрывается |
| Выбор Уровня | `GET /training/levels?role=...&topic_id=...` | Доступность вычисляет backend |
| Чат | `POST /training/levels/{level}/start?role=...&topic_id=...`, `GET /attempts/{id}` | Полный восстанавливаемый GameState |
| Result | `POST /attempts/{id}/answers`, `GET /attempts/{id}/result` | Итог сохраняется и повторно читается |
| Прогресс | `GET /progress?role=...` | Сводка роли, средний Балл завершённых Прохождений, лучший результат Уровней и десять последних завершённых Прохождений |
| Достижения/профиль | `GET /achievements`, `GET /auth/me`, `PATCH /profile/preferences` | Восемь Достижений, Серия дней, предпочтительная ветка |

## Темы и контент

Backend поставляет 12 Тем, по шесть на роль. Каждая Тема содержит пять блоков Теории, пять Quiz-вопросов и четыре опубликованных Сценария.

### Покупатель

1. `buyer-phishing-links` — Фишинговые ссылки.
2. `buyer-prepayment` — Предоплата.
3. `buyer-fake-delivery` — Поддельная доставка.
4. `buyer-off-platform` — Общение вне Avito.
5. `buyer-sms-codes` — Коды из SMS.
6. `buyer-too-good-offer` — Слишком выгодное предложение.

### Продавец

1. `seller-fake-payment` — Поддельная оплата.
2. `seller-fake-delivery` — Фальшивая доставка.
3. `seller-external-links` — Внешние ссылки.
4. `seller-confirmation-codes` — Коды подтверждения.
5. `seller-off-platform` — Общение вне Avito.
6. `seller-pressure` — Давление и спешка.

Frontend ветвится по `id`/`slug`, а отображаемый текст берёт из API. Контент не содержит действующих URL, телефонов, реквизитов или кодов и не объявляет штатные функции сервиса опасными.

## Ежедневное задание

Dashboard возвращает один сохранённый на московскую дату Снимок диалога: от двух до шести Сообщений и Ролевую ветку. До ответа frontend не получает вердикт, признаки риска и безопасное действие. Карточка на Dashboard открывает модальное окно, где Пользователь выбирает `answer=true` («это обман») или `answer=false` («ситуация безопасна») через `POST /daily-tasks/answer`.

После успешного ответа сервер возвращает сохранённый Result Ежедневного задания, включая вердикт, правильность выбора, до трёх признаков и безопасное действие, а также обновлённую Серию дней. Повторный ответ получает `409 STATE_CONFLICT`; frontend показывает уже сохранённый разбор и не отправляет повторный запрос.

## Открытие контента

1. Теория доступна сразу.
2. Quiz доступен после отметки Теории прочитанной.
3. Уровень 1 открывается после Quiz с Баллом не ниже 80.
4. Каждый следующий Уровень открывается после минимум одной Звезды на предыдущем.
5. Повторная попытка не уменьшает лучший Балл и Звёзды.
6. Свободная игра открывается независимо для `buyer` и `seller` только после L4 во всех шести Темах соответствующей роли.

Все L1–L4 реализованы. Состояния `coming_soon`, `implemented` и `availability_reason` в текущем DTO отсутствуют. `opened=false` означает закрытую прогрессией ступень; сервер дополнительно отклоняет её старт с `403`.

## GameState и отправка ответа

Старт и `GET /attempts/{id}` возвращают одно состояние с:

- `attempt_id`, `status`, `scenario_id`, `topic_id`;
- `product_context` и `mode` (`prepared|mixed|free_text`);
- `step_progress`, текущим `step` и допустимыми `options`;
- упорядоченными `messages` и `answers`;
- `can_finish_early`.

`step.counterparty_message` — видимая реплика. Внутренние `step_goal`, AI-инструкция, баллы и правильность вариантов клиенту не передаются.

`POST /attempts/{id}/answers` принимает актуальный `step_id` и ровно одно из:

- `option_id` для готового варианта;
- `free_text` длиной до 400 символов и приблизительно 220 токенов.

Для L4 и Свободной игры `finish=true` разрешён начиная с третьего свободного Ответа пользователя; пятый Ответ завершает Прохождение автоматически. Во время незавершённой Свободной игры тип собеседника скрыт и неизменен.

В Свободной игре `step_id` является номером ожидаемого хода (1–5). После успешного Ответа пользователя сервер увеличивает его; повтор старого хода получает `STALE_STEP` и не создаёт новый Ответ пользователя.

## Result, Прогресс и Серия дней

Result содержит Балл 0–100, 0–3 Звезды, разбор решений, признаки риска, безопасные действия, тематический прогресс, следующий шаг, новые Достижения и Серию дней. `is_scam` присутствует только в завершённой Свободной игре.

Звёзды:

| Балл | Звёзды |
| ---: | ---: |
| 0–54 | 0 |
| 55–69 | 1 |
| 70–84 | 2 |
| 85–100 | 3 |

Последний Ответ пользователя, Result, лучший Прогресс, завершение Темы, новые Достижения и учебная активность сохраняются одной транзакцией. Серия дней считается по календарным датам `Europe/Moscow`; несколько действий за день увеличивают её не более одного раза.

Восемь кодов Достижений стабильны: `first_training`, `five_trainings`, `perfect_score`, `first_topic_completed`, `all_buyer_topics`, `all_seller_topics`, `streak_3`, `streak_7`.

## AI

L1–L2 детерминированы. На L3 qwen3:8b оценивает свободный текст и формирует реакцию; на L4 ведёт мошеннический диалог; в Свободной игре ведёт выбранный при старте тип собеседника. Frontend не вызывает Ollama и не рассчитывает результат.

Backend ограничивает историю и бюджет контекста, требует строгий JSON и валидирует его до записи. Таймаут, переполнение контекста и невалидный ответ модели оставляют состояние неизменным, поэтому клиент может показать retry.

## Интеграционные правила frontend

- Не вычислять доступность, Балл, Звёзды, правильные ответы или `continue_action` локально.
- Не активировать ссылки из учебного контента; рендерить только структурированные блоки.
- После `401` переводить Пользователя на вход; `403` показывать как закрытый контент; `409 STALE_STEP` обновлять через `GET /attempts/{id}`.
- Блокировать двойную отправку ответа на клиенте, но не полагаться на неё как на защиту состояния.
- Для восстановления экрана чата использовать `GET /attempts/{id}`, для результата — `GET /attempts/{id}/result`.
- Генерировать типы из OpenAPI или держать ручные типы проверяемыми против него.

## Проверки handoff

Backend acceptance подтверждает:

- валидность OpenAPI и соответствие маршрутам;
- миграции `up/down/up` на чистой и существующей схеме;
- 12 Тем, 60 блоков Теории, 60 Quiz-вопросов, 240 вариантов и 48 опубликованных Сценариев;
- cookie-auth, Swagger/OpenAPI, PostgreSQL и AI boundary;
- сквозной путь от регистрации до Свободной игры;
- отсутствие побочных эффектов при ошибке AI и устаревшем `step_id`.

Swagger UI доступен по `/swagger/`, OpenAPI — по `/openapi/v1.yaml`; оба адреса защищены отдельной HTTP Basic Auth из `SWAGGER_USERNAME` и `SWAGGER_PASSWORD`.
