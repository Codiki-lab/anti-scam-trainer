Бэкенд организован тремя контейнерами в `backend/internal`: `core` с общими правилами и техническими адаптерами, `features` с продуктовыми возможностями `auth`, `scenarios`, `attempts` и `learning`, а также `tests` с проверками их публичных интерфейсов. В каждой продуктовой возможности HTTP-адаптер, сервис и PostgreSQL-репозиторий разделены физически по обязательным опорным файлам ADR-0012. `auth` владеет локальными учётными записями и аутентификацией, а `learning` — Dashboard, Прогрессом, Достижениями, Серией дней, Теорией и Quiz. `core/app` — composition root: он создаёт соединение с БД, связывает конкретные адаптеры и регистрирует их маршруты в `core/server/router` под `/api/v1`.

## Известные технические ограничения

1. Пользовательский веб-клиент поставляется отдельно; gateway ожидает production-сборку в `frontend/dist`.
2. Начальная схема находится в обратимой versioned-миграции `000001_initial_schema`. Контейнер миграций применяет её и все последующие миграции перед запуском API в Compose.
3. Калибровочный тест qwen3:8b требует локального Ollama и запускается только по `OLLAMA_PREFLIGHT_TEST=1`.
4. Сценарный admin API не возвращает сохранённые Шаги и варианты при чтении списка Сценариев. Поэтому web-админка не показывает визуальный редактор существующих Шагов, пока backend-контракт не предоставит их состав.

## Проверенный минимум

Команда ниже запускает тесты доменных правил и HTTP-контракта без PostgreSQL:

```bash
cd backend
go test ./...
```

Тесты домена проверяют переходы Прохождения, границы Звёзд, Quiz, завершение Темы, Серию дней и Достижения. HTTP-contract тесты собирают роутер с тестовыми реализациями репозиториев и проверяют аутентификацию, GameState, `STALE_STEP`, AI failure и Свободную игру.
