# ADR-0005: контейнеры core, features и tests

- Статус: принято
- Дата: 2026-08-08
- Заменяет часть ADR-0004 о размещении общих технических пакетов вне `core`

## Контекст

После появления продуктовых возможностей `users`, `chats`, `sessions` и `progress` структура `internal` содержала общие пакеты вперемешку с `features`. Тесты находились рядом с реализацией, поэтому при обзоре дерева нельзя было быстро отделить код приложения от проверок.

## Решение

В `backend/internal` поддерживаются три верхнеуровневых контейнера:

1. `core` — общие для продукта модули, не принадлежащие одной продуктовой возможности: предметные типы и правила, конфигурация, AI provider, PostgreSQL-адаптер, ошибки и HTTP-транспорт.
2. `features` — продуктовые возможности. Каждая сохраняет пакеты `http`, `service` и `repository`.
3. `tests` — тесты, сгруппированные по проверяемому модулю или контракту. Они обращаются к реализации только через её публичный интерфейс.

Точка входа остаётся в `cmd/api`, а `app_builder` — отдельным composition root в `internal`.

## Последствия

- Изменения, относящиеся к одной продуктовой возможности, локализованы в `features`.
- Общие адаптеры и правила имеют единое место в `core`.
- Тесты не получают доступ к непубличным деталям реализации; их поверхность совпадает с интерфейсом, который используют вызывающие модули.
- Проверки HTTP-контракта и доменных правил можно найти в `internal/tests` без обхода дерева реализации.
