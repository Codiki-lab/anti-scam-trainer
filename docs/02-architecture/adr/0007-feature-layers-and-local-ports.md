# ADR-0007: трёхслойные продуктовые модули и локальные порты

- Статус: принято
- Дата: 2026-08-08
- Уточняет ADR-0004

## Контекст

Для административных CRUD-возможностей рассматривалась Vertical Slice Architecture с отдельной папкой на каждый use case и прямым доступом к PostgreSQL. Она убирает прослойки, но для тренажёра не подходит как общий подход: ключевые сценарии прохождения, прогресса и оценки ответов содержат предметные правила и будут развиваться совместно.

Текущая структура уже разделяет продуктовые возможности на HTTP, сервис и PostgreSQL-репозиторий, но одинаковые контракты объявлены и в сервисе, и в HTTP-обработчике. Расположение DTO и моделей хранения не закреплено достаточно явно.

## Решение

Каждая продуктовая возможность организована тремя слоями:

```text
features/<feature>/
├── transport/http/
├── service/
└── repository/
```

`service` реализует предметные сценарии. Он определяет небольшой интерфейс репозитория в собственном файле `repository.go`; этот интерфейс описывает только нужные сервису операции. `repository` содержит PostgreSQL-адаптер, который реализует контракт сервиса.

HTTP-обработчик получает конкретный `*service.Service` и не объявляет повторяющий его интерфейс. HTTP request/response DTO принадлежат `transport/http`; модели хранения PostgreSQL принадлежат `repository`; общие предметные типы и инварианты принадлежат `core/domain`. Общий каталог `models` не создаётся.

Новые файлы выделяются по самостоятельной причине изменения. Слои не дробятся механически на папку для каждой CRUD-операции. По мере роста сервис группирует код вокруг предметных сценариев, например `start_attempt`, `submit_answer` и `finish_attempt`, а не вокруг сквозных технических операций.

Продуктовые возможности называются терминами глоссария: `scenarios`, `attempts`, `progress` и `users`. Имена существующих SQL-таблиц могут сохраняться как внутренняя деталь PostgreSQL-адаптера.

## Последствия

- Внутри одной продуктовой возможности код HTTP, предметных сценариев и хранения остаётся рядом, но имеет ясные обязанности.
- Сервис зависит от абстракции, которую сам определяет; PostgreSQL не задаёт форму прикладной логики.
- Не возникает общего набора интерфейсов или моделей, создающего неявные связи между возможностями.
- Для простого CRUD сохраняется небольшое число файлов, а сложные сценарии растут локально в своём сервисе.
- Переименование текущих пакетов `chats` и `sessions` в `scenarios` и `attempts` затрагивает импорты и должно выполняться отдельным рефакторингом с сохранением HTTP-поведения либо его согласованным обновлением.
