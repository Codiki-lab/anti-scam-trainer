# ADR-0012: единый шаблон продуктовой возможности

- Статус: принято
- Дата: 2026-08-09
- Уточняет: ADR-0007

## Контекст

ADR-0007 закрепил три слоя внутри продуктовой возможности, но не задал единый набор опорных файлов. Если дробить каждый сервис по-разному, структура становится непредсказуемой: для одной возможности появляются файлы по HTTP-операциям, для другой — по именам доменных действий, для третьей — технические разбиения без самостоятельной причины изменения.

Команде нужен простой шаблон для создания новых возможностей и ревью, не превращающий каждую операцию в отдельный пакет или файл.

## Решение

Каждая продуктовая возможность начинает с одинаковой структуры:

```text
features/<feature>/
├── transport/http/
│   └── handler.go
├── service/
│   ├── service.go
│   └── repository.go
└── repository/
    └── postgres.go
```

- `transport/http/handler.go` содержит актуальный HTTP-адаптер возможности и его DTO.
- `service/service.go` содержит прикладные сценарии и публичный сервис возможности.
- `service/repository.go` содержит локальные порты, нужные сервису для хранилища или атомарных операций.
- `repository/postgres.go` содержит PostgreSQL-адаптер, его модели хранения и преобразования.

Дополнительный файл появляется только при самостоятельной причине изменения, которую нельзя ясно сохранить в опорном файле. Например, отдельный внешний порт и его проверка или изолированный алгоритм. Дополнительный файл не создаётся механически для каждого endpoint, CRUD-метода или use case.

`core` содержит только устойчивые общие элементы: предметные типы и инварианты в `core/domain`, технические HTTP-компоненты в `core/server`, а создание и связывание зависимостей — в `core/app`. Сценарии конкретной возможности не переносятся в `core` только ради единообразия файлов.

При рефакторинге не должны одновременно существовать старый и новый HTTP-адаптеры либо сервисы одной возможности, если старый путь не зарегистрирован и не имеет объявленного периода совместимости.

## Последствия

- Новую возможность и её границы легче найти по одинаковым путям.
- Ревью проверяет прежде всего соблюдение трёх слоёв и ответственность опорных файлов.
- Сложная возможность может получить небольшой дополнительный файл, не навязывая его всем остальным.
- Временный или заменённый код должен удаляться в рамках рефакторинга, а не оставаться параллельной неактивной реализацией.
